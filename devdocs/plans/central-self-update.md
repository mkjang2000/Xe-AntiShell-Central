# 센트럴 자체 업데이트

## 대상과 완료 조건

기존 에이전트 배포는 별도 API와 신뢰 계약을 사용한다. 이번 변경은 EL9·EL10 x86_64에서 실행 중인 센트럴 한 대를 운영자가 선택한 더 높은 중앙 RPM으로 업데이트한다. 관리 콘솔과 CLI에서 공식 GitHub 릴리스를 선택할 수 있고, 오프라인 환경에서는 공개된 RPM과 서명 manifest 파일을 사용한다. 새 릴리스의 공개만으로 서버를 재시작하지 않는다.

## 실행 경로

1. 웹 관리자는 기존 계정과 CSRF 검사를 통과한다. CLI는 관리 호스트에서 실행한다. GitHub 클라이언트는 공식 센트럴 저장소에서 현재 EL용 패키지와 서명 파일을 찾는다.
2. 별도 systemd 소켓을 통해 설치할 바이트를 전달한다. 웹 서비스는 기존 비특권 계정으로 구동한다. 루트 작업자는 고정된 발행자 공개키와 센트럴 전용 서명 문맥, SHA-256, RPM 헤더, OS·아키텍처, 설치 버전을 다시 확인한다. 웹에서 로컬 경로나 명령을 지정할 수 없다.
3. 한 번에 한 작업만 접수하고 진행 상태를 루트 전용 디렉터리에 기록한다. 센트럴을 정지한 상태에서 설치 전 상태(키, DB와 WAL, 관리 설정, 릴리스 저장소)를 백업한다. 백업 실패 시 새 RPM을 설치하지 않는다.
4. 작업자는 RPM 교체 후 센트럴을 기동하고 설치 버전과 실제 프로세스·응답을 확인한다. 웹과 CLI에서 같은 상태를 조회한다. 중단된 작업을 재시도할 때는 이미 설치된 버전과 남은 백업을 확인한다. 상태 DB를 과거로 되감는 복구는 별도 운영자 판단이 필요하다. 자체 백업은 루트 전용 `/var/lib/xe-antishell-central-updater/`에 저장하며, 성공한 업데이트 뒤 최신 두 개를 보존한다. 표준 상태 경로와 loopback 운영 API를 검사하고, 백업 공간이 부족하면 업데이트를 거절한다.
5. 이전 RPM에는 업데이트 소켓이 없다. 신뢰하는 릴리스 소스에서 빌드한 CLI의 bootstrap 명령으로 첫 전환을 할 수 있다. 에이전트 릴리스나 배포 작업은 변경하지 않는다.

RPM 21에서는 전용 루트 작업자가 EL의 RPM 설치 스크립트 도메인으로 전환할 수 있도록 이 유닛에만 `NoNewPrivileges=false`를 지정한다. 센트럴 본체는 `NoNewPrivileges=true`로 실행한다. SELinux 정책과 RPM 발행자 검증 방식은 동일하다.

## 검증

공식 릴리스 검색, 서명·RPM 교체·다운그레이드 거절, 웹 권한과 CSRF, 작업 중복·중단, 백업 실패·설치 실패·재기동을 확인한다. 운영 DB 스키마 3을 바꾸는 첫 업그레이드에는 서비스 중단과 백업 복구 조건이 적용된다.

### RPM 20 후보 검증 결과

- EL9 및 EL10 x86_64 공식 RPM 빌드와 저장소의 `make verify`가 통과했다.
- SELinux Enforcing 상태인 Rocky Linux 9.9 격리 게스트에서 공개 RPM 19를 설치한 뒤 RPM 20의 bootstrap을 실행했다. 네트워크가 차단된 게스트에서는 GitHub에서 받을 두 파일을 동일한 릴리스 후보 바이트로 공급했다. 설치 후 새 센트럴 프로세스, 웹 로그인, 기존 그룹과 상태 파일 7개 보존을 확인했다. 백업을 별도 위치에 복원해 SQLite 무결성과 그룹 데이터도 확인했다.
- 웹 업데이트 경로는 같은 게스트의 별도 스냅샷에서 이전 버전 번호로 빌드한 자체 업데이트 지원 패키지로 시험했다. 관리자의 RPM·서명 파일 업로드와 백업은 성공했지만, 전용 작업자의 RPM 설치 단계에서 SELinux가 `rpm_script_t`로의 `nnp_transition`을 거절했다. 작업자는 실패를 기록하고 기존 센트럴 서비스를 다시 기동했다.
- RPM 20은 이 시험 결과에 따라 공개를 보류했다. EL10 실기 설치와 운영 센트럴의 DB 스키마 전환은 이 시험 범위에 포함하지 않았다.

### RPM 21 검증 결과

- [태그 검증](https://github.com/mkjang2000/Xe-AntiShell-Central/actions/runs/44344174116)과 [EL9·EL10 RPM 빌드](https://github.com/mkjang2000/Xe-AntiShell-Central/actions/runs/44344174074)가 통과했다. 두 RPM의 서비스 파일을 태그 소스와 비교하고, 설치본에서 센트럴 본체의 권한 제한과 전용 작업자 설정을 각각 확인했다.
- Rocky Linux 9.9에서 SELinux Enforcing을 유지한 채 별도 스냅샷으로 네 경로를 시험했다. 공개 RPM 19와 스키마 3으로 초기화한 RPM 16에서는 첫 전환 스크립트로 설치했다. 웹의 RPM·서명 파일 업로드와 CLI의 로컬 RPM 설치에는 RPM 21과 같은 작업자 설정을 실제 패키지에 포함한 시험용 선행 버전을 사용했다. 게스트에서 systemd 설정을 덮어쓰지 않았다.
- 네 경로 모두 설치 성공, 새 센트럴 PID, 웹 재로그인, 기존 그룹과 키·인증 등 상태 파일 7개 보존을 확인했다. 백업을 별도 위치에 복원해 SQLite 무결성도 검사했다. RPM 16에서 출발한 시험은 새 DB의 스키마가 4가 되고 전환 전 백업은 스키마 3으로 복원되는 것을 확인했다. 모든 데이터는 시험용이었다.
- 네트워크를 분리한 가상머신의 첫 전환 시험에서는 공식 URL 두 개의 응답을 같은 발행용 RPM과 서명 파일로 공급했다.
- Rocky Linux 10.3 Enforcing에서도 r19 태그로 빌드한 RPM의 첫 전환과 시험용 선행 RPM에서 CLI 소켓 설치와 웹 RPM·서명 업로드를 검증했다. 설치 중 RPM 스크립트의 SELinux 도메인 `rpm_script_t`를 관찰했다. 재기동 후 메인 프로세스의 `NoNewPrivs`는 1, 작업자는 0이었다.
- 공개 후 EL9·EL10에서 패키지의 CLI로 GitHub 목록을 조회했다. 각 버전에 맞는 RPM을 실제로 내려받아 크기, SHA-256, RPM 헤더와 발행자 서명을 검증했다. RPM 파일명만 제공하는 웹 경로에서도 동일한 서명 manifest가 조회됐다. 공개 자산 6개를 다시 받아 시험에 사용한 서명본과 대조했다. [센트럴 RPM 21](https://github.com/mkjang2000/Xe-AntiShell-Central/releases/tag/v0.1.0-r21)
