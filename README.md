# Xe-AntiShell-Central

[Xe-AntiShell](https://github.com/mkjang2000/Xe-AntiShell) 에이전트를 위한
독립 중앙 관리 서비스다. 에이전트 등록, mTLS 이벤트 전송과 ACK, 상태 보고,
서명 정책, 일회용 에이전트 삭제 승인 및 인증서 철회를 제공한다. 프로젝트
코드는 MIT이며, 외부 의존성 고지는 [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md)에 있다.

한국어 중앙 웹패널에서 서버 현황과 기능 지원 상태, 탐지 이력, 정책·그룹,
등록 토큰 및 일회용 삭제 승인을 관리한다. 관리자·운영자·조회자 계정과
권한을 지원한다. 자동 인증서 갱신, PostgreSQL 및 중앙 서버 다중화는 후속 범위다. 에이전트 탐지와 로컬 모니터링 패널은 별도 저장소에서
배포한다. 이 패키지는 중앙 실행 파일 하나와 전용 서비스만 설치한다.

## 빌드와 검증

Linux, Go 1.22 이상, GNU make, Bash, Git, Python 3.9 이상이 필요하다.
브라우저 스크립트 검증에는 Node.js 22 이상이 필요하며 서비스 실행에는 필요하지 않다.
검증용 race 테스트에는 C 컴파일러도 필요하다. Go 모듈은 고정 버전으로
다운로드하며, SQLite는 `modernc.org/sqlite`의 pure Go 드라이버를 사용한다.
공용 계약은 `github.com/mkjang2000/Xe-AntiShell/protocol v0.4.0`에 고정한다.

```sh
make verify
make static
./build/sentinel-central version
```

`make verify`는 소스·문서 검사, shell/패키징 회귀 검사, 형식 검사,
브라우저 스크립트 테스트, `go vet`, race 테스트와 정적 실행 파일 빌드를 수행한다. 구조는
[Project_tree.md](Project_tree.md)에 정리되어 있다.

## 설치

RPM 빌드에는 `rpm`, `rpmbuild`, systemd RPM 매크로와 GNU tar가 추가로
필요하다. 빌드는 임시 디렉터리에서 수행하며 호스트 패키지를 설치하지 않는다.
출력은 기본 `dist/rpm/`이다. 동일 파일 덮어쓰기는 `--force`로 명시한다.

```sh
make rpm
sudo ./install.sh --rpm dist/rpm/xe-antishell-central-<version>-<release>.x86_64.rpm
# 또는 현재 소스를 빌드한 뒤 설치한다.
sudo ./install.sh --build
```

설치 대상 RPM의 의존성은 사전에 설치되어 있어야 한다. 설치기는 방화벽,
PKI, DB 초기화 또는 에이전트 설정을 변경하지 않는다. 기존 `state.json`이
있으면 중앙 서비스만 활성화·시작한다. 초기 상태가 없으면 패키지만 설치하고
아래 명시적 초기화를 안내한다. 기존 `xe-antishell` 통합 RPM이 중앙 파일을
소유한다면 먼저 백업과 파일 소유권 이전을 포함한 별도 마이그레이션이 필요하다.

## 최초 초기화와 실행

**새 중앙 서버에서 한 번만** root로 실행한다. 기존 중앙 서버에서는 CA,
정책 키와 DB를 보존하고 초기화를 다시 수행하지 않는다. `init`은 기존 파일을
덮어쓰지 않는다. 원격 에이전트가 사용할 이름을 인증서 SAN에 포함한다.

```sh
sudo sentinel-central init --state-dir /var/lib/xe-antishell-central \
  --hosts localhost,127.0.0.1,::1
sudo sentinel-central init-panel --state-dir /var/lib/xe-antishell-central
sudo systemctl enable --now sentinel-central.service
```

상태는 `/var/lib/xe-antishell-central`에 저장한다. 전용 계정은
`xe-antishell-central`이며 systemd `StateDirectory`가 런타임 소유권을
관리한다. 기본 에이전트 HTTPS 주소는 `127.0.0.1:9443`, 운영자 API는
`127.0.0.1:9444`다. 기존 systemd override는 그대로 사용한다.

원격 에이전트를 받으려면 인증서 SAN과 접근 경로를 확인한 뒤 systemd
override에서 `serve --listen IP:9443 --allow-non-loopback`을 명시한다.
`--admin-listen`은 계속 loopback만 허용한다. TLS와 네트워크 접근 정책은
운영자가 별도로 구성한다.

## 중앙 웹패널

`init-panel`은 기본 사용자 `admin`의 임의 비밀번호를 생성한다. 비밀번호는
표준 출력에 표시하지 않고 상태 디렉터리의 `panel-initial-password`에
0600 권한으로 저장한다. `--username`, `--password-file`로 변경할 수 있다.
이미 존재하는 인증 파일은 덮어쓰지 않는다. 운영 중인 전용 서비스 계정으로
초기화하려면 다음과 같이 실행한다.

```sh
sudo -u xe-antishell-central sentinel-central init-panel \
  --state-dir /var/lib/xe-antishell-central
sudo systemctl restart sentinel-central.service
```

기본 주소는 `http://127.0.0.1:9089`이다. 서비스 계정이 `panel-auth.json`을
읽을 수 있어야 한다. `serve --panel-listen ''`로 패널을 끌 수 있다.
외부 접속은 `--panel-listen 0.0.0.0:9089 --allow-non-loopback-panel`로
명시한다. 에이전트 API의 `--allow-non-loopback`과는 별도 설정이다.
패널 HTTPS는 `--panel-tls-cert /path/cert.pem --panel-tls-key /path/key.pem`으로
구성한다.

Cloudflare Tunnel처럼 외부 HTTPS를 내부 HTTP로 전달한다면 `serve` 옵션에
외부 주소를 명시한다. 아래 도메인은 운영 주소로 교체한다.

```sh
sentinel-central serve --state-dir /var/lib/xe-antishell-central \
  --panel-public-origin https://console.example.com
```

기존 `--listen`, `--admin-listen`, `--panel-listen` 사용자 설정도 함께 유지한다.
Cloudflare의 서비스 유형은 **HTTP**, URL은 **127.0.0.1:9089**로 설정한다.
브라우저의 `https://console.example.com`과 내부 서비스의 `http://127.0.0.1:9089`는
서로 다른 연결이다. HTTP 패널에 HTTPS로 연결하면 502 오류가 발생한다.
HTTP Host Header override는 비워 외부 호스트 이름을 유지한다.

외부 Origin은 실제 연결 상대가 신뢰한 프록시이고 요청 Host도 일치할 때만
사용한다. 기본 프록시 범위는 같은 서버의 `127.0.0.1/32,::1/128`이며 다른
배치는 `--panel-trusted-proxies`로 정확한 CIDR을 지정한다. 외부 HTTPS 세션은
Secure 쿠키를 사용하고, localhost 포트포워딩은 기존 HTTP 접속을 유지한다.
`Forwarded`, `X-Forwarded-*`, `CF-Connecting-IP`는 신뢰하지 않는다.
이 설정은 Cloudflare Access 인증을 대신하지 않으며 콘솔 로그인·CSRF 검사는
계속 적용된다. 로그인 제한은 실제 프록시 연결 상대에 함께 적용된다.

화면에는 다음 기능이 있다.

- 전체 현황, 서버별 연결·정책 상태와 마지막 보고 시각
- CPU·메모리·디스크·I/O·네트워크·프로세스 목록과 기능 가용성
- 버전이 있는 그룹·정책 편집, 대상 미리보기 후 명시적 배포
- 탐지 / 실행·수집 / 에이전트 오류를 분리하고 기간·서버·유형·내용으로 조회
- 중앙 작업·에이전트 감사 기록을 기간별로 조회
- 계정 추가·삭제·권한 변경·비밀번호 변경 및 계정 작업 기록
- 기본 다크 테마와 로그인·콘솔 공통 라이트 전환(브라우저에 선택 저장)
- 서버 등록 토큰, 일회용 삭제 승인 파일 발급 및 등록 철회

정책에서 탐지, 차단 점수·신뢰도·필수 기능, 삭제 통제, 자원 수집과 파일 무결성을 설정한다. 차단은 호스트의 지원 기능과 로컬 차단 허용이 필요하다.

파일 무결성을 사용하려면 관리자가 서명된 RPM을 반입하고, 관리자 또는 운영자가 정책의 **에이전트 파일 무결성**에서 검사를 켜고 승인한 사이트 YAML의 SHA-256을 입력해 배포한다. 기준값을 비우면 해당 YAML은 기준 미등록으로 표시된다. 에이전트 상세의 **검사 결과 조회**에서 실행 프로그램 네 개, systemd 유닛 세 개, 사이트 YAML, 현재 서명 정책의 기대값·측정값과 측정 시각을 확인한다. 최근 두 시간 이내에 일치한 값, 예상 밖 변경, 누락, 읽기 실패, 측정 기한 경과, 승인 업데이트 후 일치를 구분한다. 이전 에이전트는 지원 미확인으로 표시한다. TPM·임의 경로·강제 무결성 항목은 후속 기능을 위한 초안으로 보관한다.

지원 에이전트에서는 **전역 root·권한 변경 탐지**를 별도로 켜고 root 실행
경보 범위를 의심 문맥만 또는 전체로 선택할 수 있다. 중앙은 현재 등록의 최신
Tetragon·탐지 엔진 지원 보고를 확인한 대상에만 새 정책을 발급한다. 엔진 지원과
실제 권한 변경 센서 수신은 구분해서 표시하며, 새 규칙의 탐지는 자동 종료 대상이
아니다. 권한 변경 세부정보는 이전·이후 UID/EUID, Capability, 사용자 namespace와
관측 결과를 구분한다. 정상 권한 복귀나 컨테이너 안의 root를 호스트 침해로
단정하지 않는다. 이전 중앙 버전으로 되돌릴 때는
[업그레이드·정책 해제 순서](devdocs/plans/central-privilege-rollout.md)를 따른다.

정책 편집기의 서비스별 파일·TCP 범위에서 보호 디렉터리, 쓰기 예외,
허용 목적지의 CIDR·포트를 지정할 수 있다. 중앙 범위 사용을 선택하면
서명한 전체 목록이 호스트 YAML 범위를 대체한다. 빈 배열은 모든 서비스의
파일·TCP 규칙을 끈다. 다음 리비전에서 중앙 범위 사용을 해제하면 호스트
YAML을 다시 사용한다. 활성 웹 서비스 이름과 일치하는 항목을 평가한다.
중앙은 대상별 최신 정책 지원 보고를 확인한다. 지원이 확인되지 않은
호스트가 있으면 대상 목록을 조정해 다시 미리보기한다. 파일·TCP 센서의
실제 이벤트 수신 시각은 서버의 기능 상태에서 별도로 확인할 수 있다.

서비스별 규칙·임시 예외 편집기에서 서비스 이름과 내장 규칙 ID를 지정하고
`enabled`, `disabled`, `suppress_until`을 선택할 수 있다. 시간제 예외는 사유와 UTC 만료 시각이 필요하다. 미리보기에서 대상과 설정을 확인한 뒤 배포한다.
해당 목록을 비우면 기본 프로필 동작을 사용한다. 서비스별 제어가 있는 정책은 중앙이 대상의 최신 `detection.service_rule_controls` 계약 1 지원을 확인한 뒤 발급한다.

그룹 편집은 정책을 자동 배포하지 않는다. 배포 미리보기 이후 정책·그룹·등록
상태가 바뀌면 다시 미리보기해야 한다. 동시에 수정한 편집 내용은 이전 버전을
덮어쓰지 않고 충돌로 알려준다. 자원 값은 최신 heartbeat의 스냅샷이며 장기
성능 시계열은 제공하지 않는다.

이력 조회는 기간·서버·유형 조건을 인덱스로 좁히며, 별도 읽기 연결을 사용해
탐색이 에이전트 하트비트·정책 쓰기 연결을 점유하지 않도록 한다. 조회 및 연결
대기는 최대 3초이며 초과하면 조건을 좁히라는 오류를 반환한다. 페이지당 개수는
1~500의 상한이며 응답은 약 8MiB 안에서 먼저 끝날 수 있다. 이때 다음 페이지로
이어 조회하면 누락 없이 계속된다. 기존 페이지 없는 관리자 API도 요청 개수
이내에서 바이트 한도로 더 적은 최신 항목을 반환할 수 있다. 전체 이력 탐색은
커서가 있는 콘솔 API를 사용한다. 최초 업그레이드 시 이력 인덱스 작성에 시간이
필요하므로 [배포·복구 계획](devdocs/plans/history-query-performance.md)을 확인한다.

삭제 승인(OTP)은 6자리 TOTP가 아니라 대상 서버·등록 세대·삭제 요청값에
묶인 짧은 유효기간의 서명 승인 파일이다. 에이전트에서 삭제 요청을 만든 뒤
그 요청값을 패널에 입력하여 파일을 발급하고 에이전트 삭제 명령에 전달한다.
정확한 명령은 아래 운영 문서를 따른다. 삭제 금지 정책이면 일반 승인을
발급하지 않는다. 등록 토큰과 승인 파일은 발급 직후 한 번만 제공되며
목록에서 다시 조회할 수 없다. 관리자와 운영자만 토큰·승인을 발급할 수 있다.

### 계정과 권한

기존 `panel-auth.json`의 관리자는 최초 업그레이드 시 `panel-accounts.db`로
가져온다. 기존 아이디와 비밀번호를 유지한다. 이후 **계정 관리**에서 계정을
추가·삭제하거나 권한과 비밀번호를 변경한다. 기본 화면은 검색 가능한 계정
목록이며, 계정 추가·상세·비밀번호 변경은 팝업에서 처리한다. 권한 옆 `?`는
마우스 올리기·키보드 포커스·클릭으로 역할별 허용 작업을 설명한다.
`panel-accounts.db`와 그 WAL 파일도
중앙 상태 백업에 포함해야 한다. 초기 비밀번호 파일은 최초 발급값이며 웹에서
변경한 비밀번호로 갱신되지 않는다.

| 역할 | 가능한 작업 |
| --- | --- |
| 관리자 | 모든 운영 작업, 계정·권한 관리 |
| 운영자 | 모니터링 조회, 그룹·정책 편집/배포, 등록·제거 승인·등록 철회 |
| 조회자 | 모니터링·정책·이력 조회 |

새 비밀번호는 최소 8자이며 영문 소문자·숫자·특수문자(ASCII 구두점)를
모두 포함해야 한다. 8~9자는 영문 대문자도 필요하고, 10자 이상에서는
대문자가 선택이다. 문자 수는 Unicode 코드 포인트 기준이며 최대 크기는
1,024 UTF-8 바이트다. 공백은 특수문자 요건으로 세지 않는다.
기존 비밀번호의 로그인은 유지되고 새 비밀번호를 지정할 때만 이 규칙을 적용한다.

모든 계정은 본인 비밀번호를 변경할 수 있다. 마지막 관리자 삭제·강등은
거부한다. 비밀번호·권한 변경 또는 삭제는 해당 계정의 기존 로그인 세션을
무효화한다. 권한은 화면과 서버 API 양쪽에 적용한다.

### 에이전트 버전과 업데이트

관리자는 `xe-antishell` RPM을 업로드·삭제할 수 있다. 중앙은 파일명 대신
RPM 헤더의 패키지·epoch·버전·release·아키텍처와 EL major를 검사하고
SHA256에 따라 보관한다. 초기 지원은 EL 7~10의 `x86_64` 에이전트이며,
파일당 64 MiB, 활성 릴리스 32개·합계 1 GiB를 제한한다. RPM 검사에는
`/usr/bin/rpm`이 필요하다. RPM scriptlet도 배포 코드이므로 업로드는 관리자
권한으로만 제공한다.

관리자와 운영자는 릴리스·개별 서버·그룹을 선택하고 중앙이 계산한 대상과
제외 사유를 미리 본 뒤 명시적으로 배포한다. 그룹·등록·설치 패키지가
미리보기 이후 바뀌면 재확인이 필요하다. 업데이트를 지원하는 에이전트를
먼저 설치하고 로컬 업데이트를 허용해야 한다. 이전 에이전트·미확인 설치
상태는 수동 초기 설치가 필요한 대상으로 표시하며, 중앙 지시만으로
로컬 비활성 설정을 우회하지 않는다. 서로 다른 OS/아키텍처, 하위 버전,
이미 실행 중인 업데이트는 제외한다.

중앙이 업데이트를 지시하면 에이전트가 기존 mTLS 연결로 받는다. 대기는
7일이며 실제 제안된 계획은 15분, 다운로드 후 별도 설치 승인은 2분이다.
기본 배포는 한 대씩 진행하고, 실패·만료·설치 결과 미확인이 발생하면
남은 미승인 대상은 중지한다. 설치 승인을 받은 작업은 취소로 중간
종료하지 않는다. 설치 승인 후 10분 동안 결과 보고가 없으면 결과 미확인
실패로 남긴다. 이는 원격 설치가 실제로 중단되었음을 뜻하지 않는다.

다운로드·지시 전달은 설치 성공과 구분한다. 목표 RPM과 새 실행 버전의
결과 보고가 있어야 성공으로 표시한다. 종료된 작업의 늦은 보고는 이력으로
남기며 기존 결과나 새 작업을 다시 진행시키지 않는다. 재등록된 에이전트는
이전 등록의 계획·파일·설치 승인을 사용할 수 없다. 기존 탐지 정책·PKI·계정과
heartbeat 형식은 유지한다.

### 이력과 정책 입력

탐지는 실행 묶음 안의 개별 탐지 단위로, 실행은 중앙에 전달되어 보존된
프로세스 이벤트 단위로 조회한다. **전체 실행**도 에이전트가 수집·보존하지
않은 시스템 전체 실행까지 포함하지는 않는다. 날짜 조건은 중앙 수신 시각
기준이며 화면에 브라우저의 시간대를 표시한다. 검색은 페이지를 나누기 전에
서버에서 수행한다.

에이전트 오류 이력은 이번 버전부터 오류 발생·변경·복구를 기록한다. 최초
업그레이드에서 남아 있던 오류는 기존 상태로 구분한다. 과거에 이미 사라진
오류는 복구할 수 없다. 오류 원문 대신 분류를 보존하며 현재 상세는 에이전트
보고에서 확인한다.

정책의 **대응에 필요한 기능**은 한국어 체크 항목으로 편집한다. 이것은
Tetragon 정책 문법이 아니라 자동 종료·모의 대응의 사전조건이다. 탐지 생성
조건과 구분하며, 사용자 정의 키는 고급 입력에 보존한다. 추천 조건 선택도
저장·배포를 자동으로 수행하지 않는다.

### 대화형 설치용 토큰

에이전트 설치 마법사에서 사용할 완전한 설치 토큰을 발급하려면 중앙 실행
옵션에 `--enrollment-url https://central.example.com:9443`을 설정한다. 이 주소는
웹패널 주소가 아니라 에이전트 HTTPS API이며, 현재 서버 인증서가 해당 이름을
포함해야 한다. 기존 CA·정책 키·DB를 지우거나 다시 초기화하지 않는다.

패널에서 발급한 설치 토큰에는 단일 대상 등록 비밀값과 중앙 URL, 에이전트 ID,
유효 시간, 공개 CA가 포함된다. 새 에이전트에서 `sudo ./install.sh`를 실행하고
그 토큰을 붙여 넣으면 인증서·복구 파일 경로를 직접 입력할 필요가 없다.
설치 토큰은 자격 증명이므로 명령 인자·로그·저장소에 넣지 않는다. 에이전트는
토큰으로 전달받은 CA로 TLS와 호스트 이름을 검증한 뒤 등록 비밀값을 전송한다.
개인 키와 오프라인 복구코드는 에이전트에서 생성하며 중앙에 원문을 보관하지 않는다.
기존 원문 토큰과 CA 파일을 전달하는 비대화형 등록 방식도 유지한다.

```sh
sudo sentinel-central enrollment-token \
  --state-dir /var/lib/xe-antishell-central \
  --agent-id HOST_ID --output-file /root/xe-enrollment-token --ttl 1h
```

토큰은 한 에이전트에 귀속되며 한 번만 사용할 수 있다. CA 공개 인증서와
토큰은 인증된 별도 경로로 해당 에이전트에 전달한다. CA·정책 개인 키는
전달하지 않는다. 운영자 자격 증명도 파일로 보관하고 명령 인자에 넣지 않는다.
등록, 서명 정책, 조회, 에이전트 삭제 승인과 오프라인 복구 절차는
[Managed v1 운영 문서](devdocs/analysis/managed-v1-operations.md)를 따른다.

## 일반 관측 이력 보존

센트럴은 수신 데이터를 검증한 뒤 구조화된 관측과 탐지 결과를 보존합니다.
새 기록에서는 원문 JSON, 프로세스 인자·작업 디렉터리, 반복되는 조상 스냅샷을
제외합니다. 일반 관측은 중앙 수신 시각부터 1시간이 지나면 순차 정리합니다.
탐지와 연결된 근거, 감사 로그, 등록·정책·업데이트 상태, 전송 ACK와 무결성
다이제스트는 그대로 보존합니다. 이전 버전의 데이터는 기동 후 작은 범위로
나눠 분류합니다.

삭제한 페이지는 SQLite의 후속 저장에 재사용됩니다. 파일 자체의 축소는
`auto_vacuum=INCREMENTAL` DB에서 제한적으로 실행됩니다. 이전 DB 변환과
롤백 범위는 [이력 보존 설계](devdocs/plans/minimal-observation-history.md)에
기록했습니다.

## 센트럴 디스크 용량 확인

`sentinel-central capacity`는 로컬 상태 디렉터리에서 DB 파일, WAL, SQLite가
사용 중인 페이지와 재사용 가능한 빈 페이지, 파일시스템 가용량, 한 시간 만료
기준을 넘긴 지연 시간과 누적 전송 순번을 JSON으로 출력합니다. 파일 크기와
사용 중인 페이지의 차이는 다음 쓰기에서 재사용할 수 있는 공간 및 WAL
체크포인트 시점의 영향을 받습니다. 원하는 간격으로 두 번 실행하면 증가분을
비교할 수 있습니다. 별도 데이터 수집이나 에이전트 업데이트는 필요하지 않습니다.

```sh
sudo -u xe-antishell-central /usr/sbin/sentinel-central capacity
sudo -u xe-antishell-central /usr/sbin/sentinel-central capacity --min-free-bytes 10737418240
```

서비스 계정으로 실행하면 SQLite가 공유 메모리 등 WAL 보조 파일을 열거나
생성할 때 서비스와 같은 권한을 사용합니다. 두 번째 예시는 가용량이 10 GiB 미만이면 같은 보고서를 출력한 뒤 실패 상태로
종료합니다. 읽기 전용 조회는 스키마 3과 4에서 동작합니다. RPM 17은 기존
영수증을 제자리에서 유지하고 새 순번부터 짧은 영수증을 저장합니다. 스키마 4의
복구 조건과 측정값은 [수신 영수증 용량 관리](devdocs/plans/compact-delivery-receipts.md)에 있습니다.

## 업그레이드와 데이터 보존

패널의 에이전트 업데이트는 서버·그룹별 대상과 제외 사유를 먼저 확인한 뒤
승인한다. 관리자는 내장 발행자 공개키로 검증되는 RPM·서명 manifest 파일을
함께 등록하거나 고정 공식 GitHub 릴리스에서 가져올 수 있다. 중앙 배포 승인
서명은 패키지 발행자 서명과 별도로 검증된다. 개인 키를 패널에 입력하지 않는다.
운영자는 검증된 릴리스의 배포·취소를 수행하고 조회자는 진행 상태를 확인한다.
자동 업데이트를 지원하지 않는 기존 에이전트에는 먼저 별도 설치가 필요하다.
기본 배포는 순차 진행하며 첫 실패·만료·결과 미확인 시 남은 미시작 대상을
중지한다. 설치 승인을 받은 작업은 취소로 중단하지 않으며, 성공에는 설치된
RPM·실행 버전·재시작 후 수집 점검이 필요하다. 자세한 계약과 제한은
[업데이트 설계](devdocs/plans/agent-update-backend.md)를 참고한다.

중앙 RPM은 `/usr/sbin/sentinel-central`, 중앙 systemd unit 및 상태
디렉터리만 소유한다. 에이전트 패키지를 요구하거나 에이전트 삭제 승인
명령을 실행하지 않는다. 패키지 삭제는 중앙 서비스만 중지하며 PKI·DB는
삭제하지 않는다. 상태는 별도로 보호하고 백업해야 한다.

SQLite 백업은 서비스를 중지한 일관된 복사 또는 SQLite backup 방식으로
수행한다. 실행 중 `central.db` 하나만 복사하면 WAL의 최근 커밋을 놓칠 수
있다. 상태 디렉터리에는 CA·정책 개인 키와 운영자 자격 증명이 함께 있다.
저장소나 소스 배포물에 실제 상태, 토큰, DB, 호스트 설정을 넣지 않는다.

RPM과 기본 unit은 Rocky/RHEL 계열 9 환경을 기준으로 준비한다. 다른 OS,
별도 호스트 간 통신 및 배포 환경별 검증은 추가로 필요하다. 이 저장소의
자동 테스트 통과는 운영 환경 전체의 검증을 의미하지 않는다.
